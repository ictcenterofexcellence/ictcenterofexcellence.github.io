MDE in real-time (PLC) context ​

Real-time code running on low-level hardware such as PLC controllers is constrained by the real-time update loop. It usually is running at a fixed update frequency - often very quickly like 1000 or 10,000 Hz - which determines the amount of time each update cycle has to finish its work.

This often imposes limitations on the kinds of programming constructs that can be used, firstly because all code must run in a very short amount of time, but also because predictability is key for immediately handling changes in the environment as they happen, spikes in update times must be avoided at all cost.

Why Model-Driven Software ​

Model-Driven Engineering for very robust software is a natural fit for the use-cases in which real-time machine control is often used: These systems are often very stateful, event-driven* and are often dangerous and/or expensive, warranting extra effort in keeping the software safe and correct.

The models created using MDE and the verification process on those models will verify that the resulting software is very robust and safe, forcing all edge cases to be handled. The main MDE tools we are familiar with are Popili/Coco and Dezyne.

Challenges with Model-Driven Software ​

Model-driven software often relies on a runtime that uses threading for its execution. Threading breaks out of the fixed update timeline, and therefore is not suitable for use in real-time contexts.

Furthermore, MDE models often rely on a system being event-driven, while PLC code is often polling-oriented: it reads out its inputs and writes outputs every update tick. These two paradigms are not trivially bridged.

Steps to use MDE software in real-time context ​

Turning sensor values into state machines ​

PLC software has to read its inputs every update tick, while MDE software relies on events. This means that in MDE software the sensor will often request the initial value of a sensor at startup, and then only relies on value changed events afterwards.

For MDE software we want to model our sensors as such:

You can make a helper class in your glue code that polls the input, checks with the value it had last update, and fire a value changed event when the value of the sensor has changed since last tick:

cpp
class DigitalIn
{
    bool currentValue;
    std::function<void(bool)> valueChanged;

    void Update() {
        // Read value from hardware
        auto newValue = ReadIO();
        if (newValue != currentValue) {
            // If value is different from last frame, send out event
            valueChanged(newValue);
        }
        // Update stored value
        currentValue = newValue;
    }
};

Then create an instance of this helper for every input, and call .Update() on every update tick. When the value of the input changes it should send the valueChanged event into the MDE software.

Modify timers to be based on the update cycle ​

Timers are often implemented using threads, or via the execution engine's thread (like is convention for Dezyne). Neither of these methods are viable. Instead, the timers should be implemented using the Update() cycle instead.

The basic (pseudo-)code for such a timer is this:

cpp
class Timer
{
    bool active{false};
    std::chrono::steady_clock::time_point deadline;

    std::function<void()> timerExpired;

    template <typename Duration>
    void Start(Duration duration)
    {
        deadline = std::chrono::steady_clock::now() + duration;
    }

    void Update()
    {
        if (active && (std::chrono::steady_clock::now() >= deadline))
        {
            // If timer is currently active and past the deadline, fire
            // expired event and set it back to inactive
            timerExpired();
            active = false;
        }
    }
};

Then just like the input classes turning the cycle updates into events, also your timers need to be updated every tick.

Remove execution shells ​

Coco ​

For Coco, the trick to getting this to work is to use their C code generation, to avoid any illegal constructions. Then after connecting the generated code to your own glue, you must drain the queue after any event sent into the system. This must be done by calling <component>_send_drain_queue(self) every time after you fire a <component>_<port>_send_<event>(self) call.

Dezyne ​

For Dezyne, the regular code generation will suffice. However, the code generation shell flag (-s) should not be used! Since all updates are running single-threaded from the update cycle, the shell is not really needed anyway. For timers that normally execute as part of the shell, see the timers section above.
